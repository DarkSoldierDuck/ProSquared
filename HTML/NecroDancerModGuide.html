How to make a simple NecroDancer mod

(Requires Synchrony DLC)

A simple mod, step-by-step

Go to menu → Customize → Mods

Select My Mods → New Mod (the plus icon)

This will take you to the Create New Mod screen:

Enter the mod name (its name as seen in the game and in public) and the namespace (how you will be referring to the mod in the code) you want.

We will create a mod that spawns an extra heart container every level, so we will name the mod "Heart Every Level". The namespace cannot have spaces, so we will put in HeartEveryLevel. With both fields entered, we are now ready to hit Create.

As you hit Create, a folder will pop up. The folder path should appear as

[your username]/AppData/Local/NecroDancer/mods/HeartEveryLevel

Inside that folder you will find a .lua file, in this case HeartEveryLevel.lua. Lua files are where you put all your code

You can open the Lua file with any text editor

(here we use NotePad++, but regular NotePad works too)

Now delete all text that comes with the file (the two lines including the "Hello world"),

paste in the following, and save:

(the code will be explained in the next section)

local event = require "necro.event.Event"

local object = require "necro.game.object.Object"

event.levelLoad.add("spawn", {order="entities"},

function (ev)

object.spawn("MiscHeartContainer",1,0)

end)

Now go back to NecroDancer and enter All Zones Mode, and there should be an extra heart right beside you in 1-1.

If you don't see it, make sure your mod is enabled by going into Menu → Customize → Mods again. The Heart Every Level mod should be lit up, like this:

(Warning: having any mods active will disable all leaderboards and achievements. To revert to unmodded, go to menu → Customize and select Restore Default Gameplay.)

What’s in the code? - HeartEveryLevel

The Lua code is split into two parts: the require statements and the main section

We focus on the main section first:

The object.spawn function creates a Heart Container, and places it 1 tile to the right of the player’s starting position. MiscHeartContainer is the internal name for the Heart Container item. The (1,0) are the coordinates relative to the starting position.

The levelLoad in Line 4 means “at the start of every level”. More precisely, we are adding the contents of function (ev) (which is just Line 6 in this case) to the levelLoad event, which fires every time a new level starts.

Taken together, this code block spawns a Heart Container at the start of every level.

A closer look at event.levelLoad.add:

The first argument “spawn” is the name of the handler we are registering, and you can choose any name that describes what this block does, such as spawnHeart or spawnItems. The name needs to be unique within the mod.

The second argument {order="entities"} contains the event parameters; here only one parameter, order, is specified. This parameter determines how early or late function(ev) will be run within the levelLoad event. (More on this later)

The third argument function (ev)... end is the actual function that will be run whenever an event ev fires. In this case, there is just one level-loading event ev every time a level starts. If we had instead, say event.objectDealDamage.add, then there would be one ev every time something deals damage.

Because we are using functions from the ‘event’ and ‘object’ modules, we need to include these modules in the require statements. The "necro.event.Event" is the name of the ‘event’ module as the game knows it internally, and the event in front is a name we give to this module so we can refer to it. This is what allowed us to use the function event.levelLoad.add in Line 4.

Which require statements to include in your code depends on the functions you want to use in your mod. Strictly speaking, you can have a require statement anywhere before the first time you use a function from that module, but the convention is to simply put all require statements at the very start.

Now let’s say we also want to spawn some cookies. To find the internal name for cookies, we can use the built-in Level Editor.

Go to menu → Customize → Downloadable Content

On the top row there are 5 icons, including one that looks like an eye (“Show feature packs”). Make sure it is turned on, and select and enable Level Editor under Feature Packs.

Now exit the menu, and right click anywhere. This will bring up the Level Editor overlay. Click on the gear icon on top (“Editor Options…”)

Scroll down on the Editor Options menu, and check Show Internal Object Names

Exit the menu, and now the internal names will appear as you hover over objects on the right. You can also press Ctrl + F and look for a specific item:

Now that we know cookies are known as FoodCookies internally, we can use this in our code.

Save, make sure the mod is active, enter All Zones Mode again, and there should now be cookies in addition to the heart container.

Components and Filters - SkeletonBuff

Let’s say we want all skeletons to do more damage. As before, we create a new mod from the in-game menu, this time with mod name Skeleton Buff and namespace SkeletonBuff. We hit create, and open SkeletonBuff.lua in the folder that pops up.

We need a way to refer to all skeletons. To do so, we add a component, which we will name damageBuff, to all skeleton entities. This component will serve as a marker, so we can easily refer to this group of enemies to apply damage buff to them.

Before we can add a component, we must register it.

This registers a component named damageBuff. Everywhere else in the code, this component will be referred to as SkeletonBuff_damageBuff, since SkeletonBuff is the namespace of the mod. (The namespace distinguishes it from other components that may also have been named damageBuff in the game itself and in other mods. The code will not run correctly if the components aren’t prefixed with the namespace!)

Lua is case-sensitive, so if you register the component as damageBuff, but later on write SkeletonBuff_DamageBuff, this will give you an error. Try to keep a consistent style - for example always start component names with a lowercase letter - to reduce the chance of making mistakes.

Now that the component is registered, we can add it to all skeleton entities.

Compare this with the levelLoad code we had in the HeartEveryLevel example; even though the code is split into more lines this time (so it all fits on the screen), it has the same overall structure as before. The "addSkeletonBuffComponent" is a descriptive name we give to this handler.

The entitySchemaLoadNamedEnemy event fires whenever an enemy of a certain kind is loaded, specified by the key = "skeleton" parameter. In Line 17, ev is the skeleton-loading event itself, and ev.entity refers to the skeleton entity that’s being loaded. This line adds the component SkeletonBuff_damageBuff to the skeleton entity. This is iterated over all skeleton-loading events ev, giving all skeleton entities the component.

Now that we have a component that lets us refer to all skeletons, we can use it to filter for events where damage is dealt by a skeleton.

Normally function(ev) would have been called every time any object deals damage, but because of the filter, it only applies when an entity with the SkeletonBuff_damageBuff component (that is, a skeleton) deals damage. The function(ev) itself increases the damage of the event by 1, or half a heart.

More on order and sequence:

The order = "baseIncrease" specifies when the damage-increasing function (ev) will be run within the objectDealDamage event. The full list of “order” (steps) in an event can be found on the searchable Synchrony API documentation page, also accessible from the in-game menu:

Object - Synchrony API Documentation (vortexbuffer.com)

If you go through this link, under event.objectDealDamage you will find all the steps in an objectDealDamage event, including baseIncrease. When deciding on which order = ... value to use, try to pick a step that makes sense for the function(ev) you are adding. If you have multiple handlers that use the same event and have the same order value, you can further specify which one will happen first by adding sequence = 1, sequence = 2, etc. to each handler. A negative value means that function(ev) will be applied before the handlers in NecroDancer that are normally in that step, while a positive value means after.

Putting it all together…

local components = require "necro.game.data.Components"

local constant = components.constant

local field = components.field

local event = require "necro.event.Event"

components.register{

        damageBuff = {},

}

event.entitySchemaLoadNamedEnemy.add(

"addSkeletonBuffComponent",

{key = "skeleton", sequence = 1},

function (ev)

        ev.entity.SkeletonBuff_damageBuff = {}

end)

event.objectDealDamage.add("increaseSkeletonDamage",

{order = "baseIncrease", filter = "SkeletonBuff_damageBuff"},

function (ev)

        ev.damage = ev.damage + 1

end)

Save, enable the mod in NecroDancer, and now skeletons will do more damage.

Creating a new entity - GlowySkeleton

To create a new entity (enemy, item, etc) based on an existing one, we use the CustomEntities module:

This defines a new entity named GlowySkeleton, with all the attributes of a white skeleton (that’s the template = ...) except for the ones we specified in components = {...}. Here only the friendly name (the name that appears in game) and innate damage value are changed. The name in Line 7 and damage are examples of component fields. These two are existing components fields built into the base game itself. For example, damage is listed under innateAttack on the API docs, which means damage is a field within the component innateAttack.

If you look at the API page closely, you will see that damage is a constant field (const int), which means it cannot be altered once defined. This means that trying to alter an enemy’s damage value by writing, say [skeleton entity].InnateAttack.damage = 3, will result in an error. Instead, you can add a damage-altering handler to the objectDealDamage event, like we do in both SkeletonBuff and GlowySkeleton.

Since we haven’t done anything with the sprites yet, this new enemy will appear and move like a white skeleton, but it will do 1 heart of damage instead of just 0.5 (assuming you turned off SkeletonBuff, that is!) We can verify this by spawning in a glowy skeleton at the start of the level:

Notice unlike MiscHeartContainer before, here we need to prefix the name of the new enemy (second GlowySkeleton) with the namespace of the mod (first GlowySkeleton). This is true for all entities and components defined within the mod. Also remember that you need to save the Lua file and restart the level for the change to take effect, since the levelLoad event only fires at level start.

We want the skeleton to glow once every 4 beats, and deal more damage while glowing. To track this, we register a component named glowy to add to all glowy skeletons.

Unlike the damageBuff component from SkeletonBuff which does not have fields, glowy has an int32 (integer) field called turn that tracks the number of turns until the skeleton glows. This field can be accessed via [skeleton entity].GlowySkeleton_glowy.turn. Aside from giving us a way to access the turn field, the component GlowySkeleton_glowy also serves as a marker for all glowy skeletons, and we can use it to filter for events, just like we did with SkeletonBuff_damageBuff.

The --turns until glowy in Line 7 is a comment; anything after -- is not part of the code. Comments are useful for reminding yourself (or communicating to others) what the code does.

Adding this new component to our custom entity from earlier…

Note that our custom component glowy uses the same syntax as the components built into the base game (such as innateAttack), with the only difference being the namespace prefix. Multiple fields within the same component are separated by commas; see for example the sprite component below.

To make the skeleton glow, we need a spritesheet. The original spritesheets can be found in [local files folder for NecroDancer]\data\entities. If you open skeleton.png inside that folder, you will see two rows of 16 sprites each, organized like this:

Let’s say we have this spritesheet for the glowy skeleton, with file name glowyskeleton.png

Note that you will need a graphical tool that allows for transparent background. Art programs that have transparency include Aseprite, Clip Studio Paint, and the free program GIMP.

Inside our main mod folder, we make a new folder named sprites where we can put all our spritesheets. Now we can specify the spritesheet in the code:

The texture field within the sprite component specifies the file path where the spritesheet can be found. For custom assets, the file path starts from mods, then to the path of folders that leads to the file (in this case, GlowySkeleton → sprites). If the file glowyskeleton.png cannot be found at the given location, the entity will show up as a white square.

The width and height fields are the dimensions for each individual sprite or frame on the spritesheet, in pixels. (Strictly speaking, it is not necessary to re-specify width and height here, since our sprites have the same dimensions as those for white skeletons.)

The original white skeleton sprites are animated in groups of 4: frames 1-4 are used when a skeleton has its arms down, 5-8 when the arms are up, etc. We extend our spritesheet so there are 4 extra frames (#17 thru 20) after the original 16, to be used as a glowy skeleton’s animation when it is glowing.

The built-in component customAnimations lets us specify frames to use for a custom animation, which can then be turned on or off by setting [entity].customAnimations.active to true or false.

Now, a few things need to happen every turn: the turns-until-glowy counter needs to be updated, and the skeleton’s animation needs to be updated based on the counter.

The turn event fires once a turn.

Actually, that’s not quite true. In multiplayer, there is one turn event per song beat for regular speed characters, and one turn event every time a character like Bard moves. In addition, tapping more than once per beat can also generate extra turn events, even though those extra “missed beat” events won’t belong to any player (ev.isPlayerTurn is nil instead of true). Inside a turn event, it is important to check if an entity is active, that is, if the turn event should affect it. See entity.gameObject.active line below.

We need a way to iterate over all glowy skeletons. Unlike the objectTakeDamage event, the turn event does not have an ev.entity to apply filter to. But there is another way to access and iterate over all entities with a certain component: we can use the entitiesWithComponents function in the Entities module.

The purple boxes say “at the end of every turn”, while the green boxes (the for loop) say “for every glowy skeleton entity”. Inside the for loop, we need to update the skeleton’s turns-until-glowy field and its customAnimation.active field, which dictates whether it will appear glowy.

Remember we can access the turns-until-glowy field (turn) within the component glowy via entity.GlowySkeleton_glowy.turn.

The first and last lines (if entity.gameObject.active then ... end) check whether the skeleton entity is active during this turn event; if not, the entire code block is ignored. This is important, because we don’t want all those turn events produced by a distant Bard (among other things) to affect a skeleton’s glowy status.

Note that a double equal sign == is used for comparison, whereas a single equal sign = is used to set the value of a field to something. The first half of the code (before else) says if the counter is at 0, then the skeleton has done glowing, so the counter is set to 3. The skeleton will no longer use the custom glowy animation; we specify this by setting the skeleton’s customAnimation.active field to false.

The second half (else and after) says if the counter is not at 0, then it is decremented by 1. Then, if the counter is at 0 after the decrement, then the skeleton will start glowing. The entity.beatDelay.counter = 0 line allows the skeleton to attack immediately. This matches up with the fact that we only have glowy animation (frames 17-20) for the skeleton in its arms-up state.

A few details:

The order we picked for this handler (“nextTurnEffect”) comes into play here: on the API page for the turn event, nextTurnEffect is listed after both player and enemy actions (which include attacking and dealing damage), but before the animations and visuals are updated. This is why the animations should start or stop glowing based on the turn counter’s value after it is updated in the nextTurnEffect step.

The entity.beatDelay.counter = 0 line is really a fix for a subtle issue, and the reader is encouraged to try running the code (provided at end of section) without this line. Normally the 4 beat cycle of glowy status and the 2 beat cycle of arms-up / arms-down line up, and the skeleton always puts its arms up when it glows. But if the skeleton gets stuck behind a wall, it puts its arms up every turn instead of every other turn, breaking this pattern. When the skeleton gets unstuck and goes back to its 2 beat cycle again, the cycles can line up in the wrong way so that the skeleton always has its arms down when glowing. (But it will look like its arms are up, because that’s the only glowy animation we have!) Setting the beatDelay counter to 0 whenever the skeleton glows effectively forces the two cycles to line up with each other, so this issue is averted.

Putting it together:

Adding damage is easy, and only requires some minor modifications on the SkeletonBuff code. The filter is now the glowy component, and there is a further check in Line 27 on whether the skeleton is currently glowing.

And we’re done! Here’s GlowySkeleton in its entirety:

local components = require "necro.game.data.Components"

local constant = components.constant

local field = components.field

local customEntities = require "necro.game.data.CustomEntities"

local event = require "necro.event.Event"

local ecs = require "system.game.Entities"        

local object = require "necro.game.object.Object"

components.register{

        glowy = {

                field.int32("turn", 0), --turns until glowy

        },

}        

--new custom entity based on template

customEntities.extend{

        name = "GlowySkeleton",

        template = customEntities.template.enemy("skeleton", 1),  --white skeleton

        components = {

                friendlyName = {name = "Glowy Skeleton"},

                innateAttack = {damage = 2},         --1 heart of damage

                GlowySkeleton_glowy = {turn = 0},    --custom component, 'turn' is how many turns until glowy

                sprite = {

                        texture = "mods/GlowySkeleton/sprites/glowyskeleton.png",

                        width = 24,

                        height = 28,

                        },

                customAnimation = {frames = {17,18,19,20}},   --glowy animation frames

                }

        }

--does 1 more heart of damage when glowy

event.objectDealDamage.add("glowyDamage",

{order = "baseIncrease", filter = "GlowySkeleton_glowy"},

function (ev)

        if ev.entity.GlowySkeleton_glowy.turn == 0 then

                ev.damage = ev.damage + 2

        end

end)

        

--updates the turns-until-glowy counter and glowy animation, every turn and for each glowy skeleton        

event.turn.add("updateGlowyStatus",

{order = "nextTurnEffect"},

function(ev)

        for entity in ecs.entitiesWithComponents{"GlowySkeleton_glowy"} do

                if entity.gameObject.active then      --if tracking the player whose turn it is

                        if entity.GlowySkeleton_glowy.turn == 0 then

                                entity.GlowySkeleton_glowy.turn = 3

                                entity.customAnimation.active = false   --stop glowing

                        else

                                entity.GlowySkeleton_glowy.turn = entity.GlowySkeleton_glowy.turn - 1

                                if entity.GlowySkeleton_glowy.turn == 0 then

                                        entity.customAnimation.active = true    --start glowing

                                        entity.beatDelay.counter = 0     --can attack immediately

                                end

                        end

                end        

        end

end)

                

--spawns a glowy skeleton for testing

event.levelLoad.add("spawn", {order="entities"},

function (ev)

        object.spawn("GlowySkeleton_GlowySkeleton",2,2)

end)

x.1. Using print(ev)

The debug console can be opened by pressing Ctrl + Shift + F1. The print function writes to the debug console: print("ABC") results in (note that the first tab Output is selected):

A print statement inside a handler tells you when a handler isn’t running as expected, by the absence of the print result. It can also tell you the value of a variable, such as with print(ev.entity.name) (or whichever component you want to inspect). Note that if the printed messages are too long to be viewed on the debug console, as is often the case when printing an entity or entitySchema stuff, you can also find the output in the NecroDancer.log file, located at Program Files (x86)\Steam\steamapps\common\Crypt of the NecroDancer\Necrodancer64\NecroDancer.log

x.2 Creating an entity dump

An entity dump can be created by running this code

event.entitySchemaLoadEntity.add("EntityDump", {order = "finalize", sequence = 1}, function(ev)

         print(ev)

end)

As you save the lua file, the game may seem to freeze for a second, because the amount of text printed out is very large! Rememeber to delete this code afterwards so it doesn't run every time.
